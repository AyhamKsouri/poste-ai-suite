Préparé par Ayham Ksouri & Yassine Jouini

Statut Prototype local, bout en bout

Deux modules d'intelligence artificielle sur une seule plateforme : un assistant IA (RAG) qui répond aux questions des agents à partir des procédures internes avec citation des sources, et un module de triage des réclamations qui classe, priorise, résume et rédige une réponse à chaque réclamation client avant validation humaine. Les deux sont opérationnels de bout en bout — authentification, base de données, API, interface — et versionnés dans un dépôt Git.

Le service IA est le seul point d'accès aux réponses générées : il tente d'abord un appel réel à Groq, et bascule automatiquement sur une logique de repli si aucune clé n'est configurée ou si l'appel échoue — le reste de l'application n'a jamais connaissance de la distinction. La base de données SQLite est utilisée directement par le backend (comptes, réclamations, historique) ; seul l'index de récupération alimente le service IA pour l'assistant RAG.

Module A — Assistant IA (RAG)

L'administrateur téléverse un document de procédure (PDF, DOCX ou TXT). Le texte est extrait, découpé en segments d'environ 500 mots avec chevauchement de 50 mots, puis indexé. Un agent pose une question en langage naturel ; le système retrouve les segments les plus pertinents et génère une réponse citant le ou les documents sources. En dessous d'un seuil de pertinence, l'assistant indique explicitement qu'il ne trouve pas l'information plutôt que d'inventer une réponse. Chaque réponse peut être notée utile / pas utile par l'agent, et l'administrateur dispose de statistiques (questions les plus posées, temps de réponse moyen, taux de satisfaction).

Module B — Triage des réclamations

Un agent soumet le texte brut d'une réclamation. L'IA la classe automatiquement parmi cinq catégories (retard de livraison, colis perdu, facturation, article endommagé, autre), évalue son urgence (faible / moyenne / élevée), la résume en 2-3 phrases, et rédige un brouillon de réponse. L'agent relit, modifie si besoin, puis approuve l'envoi — rien n'est envoyé au client sans validation humaine. Le brouillon IA et la réponse finalement envoyée sont conservés séparément dans la base, pour traçabilité.

Refonte de l'interface

L'interface est passée d'un habillage Tailwind générique à une identité dédiée, dérivée de la charte de La Poste Tunisienne (bleu marine / or) et produite à partir d'une maquette générée avec Google Stitch puis intégrée manuellement au code React existant — la logique métier (appels API, état, routage) n'a pas changé, seul l'habillage visuel a été remplacé, page par page, chaque page faisant l'objet d'un commit séparé.

Système de design

Palette, typographie (Geist), rayons et espacements centralisés dans tailwind.config.js plutôt que des couleurs codées en dur page par page.

Navigation persistante

Barre latérale bleu marine fixe avec état actif marqué d'un liseré or, remplaçant l'ancien en-tête horizontal — cohérente sur les six pages.

Tableau de bord graphique

Les barres faites main ont été remplacées par de vrais graphiques Chart.js (barres, anneau), toujours alimentés par les données réelles de l'API — aucun chiffre de la maquette n'a été conservé.

Import de documents

La page Documents gagne un glisser-déposer fonctionnel en plus du sélecteur de fichier existant, sur le même endpoint d'upload.

Conception du système IA

C'est la partie la plus significative techniquement — cinq choix de conception délibérés :

Modèle & intégration

Appels via le SDK Python officiel Groq, modèle openai/gpt-oss-120b (configurable par la variable d'environnement GROQ_MODEL). Les réponses de classification utilisent les sorties structurées (response_format JSON Schema strict) : le modèle est contraint à retourner un JSON valide et typé (catégorie, urgence, résumé, brouillon), éliminant le risque de parsing fragile.

Pipeline RAG

Récupération par TF-IDF + similarité cosinus (scikit-learn) sur les segments indexés, avec un seuil de pertinence minimal : si rien ne dépasse le seuil, l'assistant répond qu'il ne sait pas au lieu de générer une réponse non fondée — c'est le garde-fou anti-hallucination du module A.

Sécurité anti-injection

Chaque prompt système instruit explicitement le modèle de traiter le contenu fourni par l'utilisateur (texte de réclamation, extraits de documents) comme des données à analyser, jamais comme des instructions à exécuter — nécessaire puisque ce contenu provient d'utilisateurs externes non fiables.

Robustesse par repli

Sans clé API, ou si un appel échoue ou est refusé par le modèle, le système bascule automatiquement sur une logique déterministe (classification par mots-clés, réponse gabarit) — l'application ne plante jamais à cause d'un aléa du fournisseur IA, et reste démontrable hors ligne.

Réglage coût / latence

Chaque appel est plafonné à max_completion_tokens=1024 pour des réponses rapides et prévisibles côté coût. Si le modèle refuse la requête (finish_reason == "content_filter"), le système bascule aussi sur le repli déterministe. Les prompts demandent explicitement une réponse dans la langue de la question ou de la réclamation (le français, en pratique).

État actuel

Le prototype tourne actuellement en mode démonstration (sans clé Groq configurée) : la classification et les réponses utilisent une logique déterministe plutôt que des appels réels à Groq. L'intégralité du code d'intégration Groq est écrite, testée dans son chemin d'échec, et s'active immédiatement dès qu'une clé GROQ_API_KEY est renseignée dans backend/.env — aucune modification de code n'est nécessaire.
